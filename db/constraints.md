# Обоснование ограничений

## Как заполнять

- **CHECK, UNIQUE, FK** — обосновывать обязательно. Ссылка на `BR-N.M` + краткое «почему».
- **NOT NULL** — обосновывать **только** когда бизнес явно требует. Очевидные случаи (PK, FK на NOT NULL поле, поля из BR с явным «обязательно») — не дублировать.
- **NULL** (где разрешено) — обосновывать, потому что это осознанное решение, а не забывчивость.
- **DEFAULT, GENERATED** — кратко, если не очевидно.

**Правило:** если не можешь указать `BR-N.M` — либо ограничение лишнее, либо пропущено бизнес-правило. Разберись, прежде чем оставлять.

**Формат обоснования:** «<что ограничиваем> — потому что <BR-N.M> требует <что>».

Пример хорошего обоснования:

> `CHECK (rating BETWEEN 0 AND 5)` на `restaurant.rating` — потому что BR-4.2 задаёт диапазон рейтинга.

> `UNIQUE (address_id)` на `restaurant` — потому что BR-3.3 запрещает двум ресторанам делить один адрес.

> `FK (restaurant_id) → restaurant(restaurant_id)` на `product` — потому что BR-5.1 требует, чтобы блюдо принадлежало ресторану.

Пример плохого обоснования (не принимается):

> `NOT NULL` на `name` — потому что имя должно быть.

> `CHECK` на `price` — потому что цена не может быть отрицательной.

(Второе — обоснование «здравым смыслом», а не ссылкой на BR. Не принимается.)

## Ловушки

Здесь — не готовые решения, а **фиксация того, как ты решил** каждую ловушку. Преподаватель читает, чтобы понять ход мысли.

### Ловушка 1: `payment` — неполная сущность

**Какие атрибуты добавил в `payment` и почему** (BR-8.2):

```
На концептуальной диаграмме таблица payment содержит только payment_id и order_id.
На основании BR-8.2 добавлены атрибуты payment_type, amount, transaction_id, transaction_timestamp и status.
Тип оплаты хранится в payment, поскольку BR-8.6 допускает несколько попыток оплаты одного заказа разными способами.
Для выполнения BR-8.1 используется ограничение EXCLUDE USING gist (order_id WITH =) WHERE (status = 'успех').
Оно запрещает более одной успешной оплаты одного заказа, но допускает неуспешне попытки оплаты.
Для работы ограничения используется расширение btree_gist.
В payment.amount хранится итоговая сумма заказа.
Соответствие payment.amount и order.total_amount по BR-8.4 планируется контролировать триггером, 
поскольку CHECK не может обращаться к другой таблице
```

**Где хранится тип оплаты — `payment` или `order`** (BR-8.6):

```
Тип оплаты хранится в таблице payment в атрибуте payment_type. 
Согласно BR-8.6, у одного заказа может быть несколько попыток оплаты разными способами, 
поэтому тип оплаты относится к конкретной попытке платежа, 
а не к заказу в целом. 
Хранение payment_type в таблице order 
не позволит корректно отражать историю попыток оплаты.
```

### Ловушка 2: `order.address_id` — принадлежность клиенту (BR-7.4)

**Как обеспечено, что адрес доставки принадлежит клиенту:**

```
Для реализации BR-7.4 используется составной внешний ключ (client_id, address_id) таблицы order
на составной первичный ключ таблицы client_address. Это дает то,
что клиент не сможет оформить заказ на адрес, который ему не принадлежит
```

### Ловушка 3: `order_structure` — один ресторан в заказе (BR-7.3)

**Как обеспечено, что все блюда из `order.restaurant_id`:**

```
Для реализации BR-7.3 выбран механизм проверки принадлежности блюда ресторану через триггер.
При добавлении или изменении позиции заказа идеь проверка на совпадение product.restaurant_id и order.restaurant_id.
Также необходимо контролировать изменения restaurant_id у существующих заказов и блюд
```

### Ловушка 4: `review` — полиморфизм (BR-9.1)

**Как реализована валидность `review.entity_id`:**

```
Планируется использовать полиморфизм.
Поле entity_type определяет тип объекта (блюдо, ресторан или заказ), entity_id содержит UUID соответствующего объекта.
Внешний ключ для entity_id не подхожит, поскольку он может ссылаться на разные таблицы. 
Поэтому для реализации BR-9.2 планируется использовать триггер.
При добавлении или изменении отзыва триггер будет проверять существование объекта, 
принадлежность отзыва клиенту соответствующего заказа и связь объекта с этим заказом.
Дополнительно необходимо контролировать изменение связанных записей, чтобы сохранённые отзывы не теряли корректность.
Для выполнения BR-9.5 используется составное UNIQUE ограничение (order_id, entity_type, entity_id), 
которое позволяет создавать один отзыв на каждый объект 
```

## Нормализация (3НФ)

Короткое обоснование, что все таблицы в 3НФ:

```
При проектировании БД таблицы разделены по сущностям, чтобы избежать дублирования данных и обеспечить соответствие 3НФ.
Таблицы client_address, order_structure и courier_pay используют составные первичные ключи, 
исключающие дублирование записей. Остальные атрибуты зависят от ключей соответствующих таблиц.
Поля commission и total_amount рассчитываются автоматически через GENERATED ALWAYS AS STORED.
Рейтинги блюд и ресторанов хранятся отдельно и пересчитываются при изменении отзывов.
В таблице review используется полиморфная связь через entity_type и entity_id.

Особые случаи:
- order.commission — рассчитывается как 10% от order_amount через GENERATED ALWAYS AS STORED.
Это обеспечит корректность расчета комиссии

- order.total_amount — рассчитывается как сумма order_amount и комиссии. Используется GENERATED ALWAYS AS STORED,
чтобы итоговая сумма всегда соответствовала итоговой стоимости заказа

- product.rating и restaurant.rating — агрегированные значения рейтингов, которые поддерживаются триггером.
Это планируется сделать для ухода от постоянного вычисления среднего рейтинга по отзывам

- review.entity_id и review.entity_type — используют полиморфную связь с блюдами, ресторанами и заказами.
Такой подход будет требовать доп проверки ссылочной целостности через триггер,
но позволит ссылаться на несколько таблиц, чего обычный FK сделать не сможет
```
